# 거래소 2~3개 추가를 위한 용량·성능 산정

## 권장안

현재 BTCUSDT·ETHUSDT·SOLUSDT 세 종목, 현재와 비슷한 호가 주기·깊이, 거래·펀딩·미결제약정 수집과 원격 보관을 유지한다면 **신규 총 500GB CB1/CB2 SSD**를 권장한다. 하나의 볼륨으로 구성하면 500GB, I/O 격리를 우선하면 **300GB NATS + 200GB 코인 SQLite/Parquet**다. 이는 기존 10GB·20GB를 제외한 추가 용량이다.

경제적인 시작안은 300GB 한 개다. 다만 정상 평균의 약 5배 유입까지 고려하는 5~6거래소 수집·매매 동시 운영에는 500GB를 선택한다. 이 추천은 공급 성능과 측정 부하를 이용한 설계 판단이며, 새 거래소의 실제 호가 규격과 전략이 정해지기 전 수학적으로 유일한 최적값이나 무중단 보장을 의미하지 않는다.

## 실제 측정

2026-10-03 10:07:35~10:08:36 KST, 약 60.90초 동안 읽기 전용 상태 조회 3회와 최근 Parquet 원장 집계를 실시했다. 운영 설정 변경, 벤치마크 부하, 주문 전송은 하지 않았다. 데이터 용량의 GB/MB는 십진 단위이고 파일시스템 여유 GiB/MiB는 이진 단위다.

서버 메타데이터: `SVR.VSVR.AMD.HICPU.C002.M004.G003`, KVM, 2 vCPU·4GB RAM. 10GB 시스템 볼륨과 20GB 데이터 볼륨이 연결되어 있다.

약 100 IOPS 포화는 작은 CB 볼륨의 기준 성능과 부합한다. 다만 콘솔의 기존 볼륨 SKU·크레딧 잔량을 직접 읽지는 않았으므로, 크레딧 소진을 확정하지 않는다. 포화 구간의 완료 103 IOPS는 입력 작업의 실제 요구량이나 피크 수요의 상한이 아니다.

## 예상 데이터 흐름

동일 관측 구간에서 Binance 41.1건/s·0.163MB/s, Bitget 63.1건/s·0.146MB/s, Bybit 77.5건/s·0.127MB/s였다. 합계 **181.7건/s, 내부 직렬화 전송량 0.436MB/s**다. 내부 값에는 정규화 필드와 보존 원문이 포함되며 인터넷 회선 수신량과 다르다. 물리 NIC 수신은 같은 구간 약 0.160MB/s였다.

최근 정상 수집 10분의 Parquet는 30,730,503바이트다. 하루 환산 약 **4.43GB/일**, 거래소당 1.16~1.91GB/일이다. 최근 24시간 원장에는 약 4.76GB가 기록됐지만 Binance가 중단된 시간이 포함되어 있으므로 그 평균을 정상 3거래소 기준으로 사용하지 않았다. Parquet 압축은 현재 Zstandard다.

| 시나리오 | 현재 방식 기준 이벤트 | 내부 전송 | 압축 Parquet/일 | 평균의 5배 설계 유입 |
|---|---:|---:|---:|---:|
| 현재 3거래소 | 약 182건/s | 0.44MB/s | 4.43GB | 약 910건/s |
| 2개 추가, 총 5개 | 약 303건/s | 0.73MB/s | 7.38GB | 약 1,515건/s |
| 3개 추가, 총 6개 | 약 363건/s | 0.87MB/s | 8.85GB | 약 1,815건/s |

추가 거래소의 이름·채널 주기·호가 깊이는 아직 정해지지 않았다. 위 표는 기존 세 거래소 평균을 비례 확대한 예상이며 특정 거래소의 실측이 아니다. 정상 저장 예산은 전체 **7~10GB/일**, 활발한 구간에는 **10~15GB/일**, 단기 5배 유입을 별도 시험 조건으로 둔다. 거래소마다 메시지 배치 방식이 달라 메시지 수와 이벤트 수도 다를 수 있다.

호가 데이터가 최근 10분 압축 용량의 약 90%를 차지한다. 같은 종목이라도 100ms에서 10ms로 바꾸거나 매 프레임 깊은 전체 호가를 저장하면 단순 거래소 수 비례식이 맞지 않는다. 실시간 주문량은 전략에 따라 달라 별도 산정해야 하지만, 통상 저장 용량보다 주문 상태의 확정·지연·호가 최신성이 주요 설계 항목이다.

## 용량만으로 계산한 하한

원격 보관 정상 시 로컬 잔량은 작다. 원격 보관이 72시간 지연되고 총 6거래소의 평균 2배가 지속된다는 조건으로 계산하면 다음과 같다.

`(9GB/일 × 3일 × 2 + 상태 DB 12GB + 임시/복구 여유 10GB + 큐 예산 4GB) ÷ 0.70 ≈ 114GB`

따라서 이 조건의 공간 하한은 약 120GB이고, 실제 구성은 **150~200GB**가 적절하다. 72시간 전체가 5배 유입이면 같은 식이 약 230GB가 되어 300GB 수준이 필요하다. 이 수치는 미래 DB 크기를 정확히 예측한 값이 아니라 현재 약 1.95GB DB와 12시간 중복 확인 기간을 고려해 상태 공간에 여유를 배정한 예산이다.

정상 유입 기준 7일 로컬 보관이면 압축 데이터 약 62GB, 30일이면 약 266GB다. 30일 데이터를 모두 로컬에 유지하고 두 배 저장량 여유까지 원하면 800GB~1TB로 다시 산정해야 한다. 원격 보관소 누적 데이터에는 블록 스토리지와 별도의 저장 비용이 발생한다.

## 500GB를 권장하는 이유

이 서버는 KVM g3이므로 XEN SSD의 10~100GB/4,000 IOPS 규칙을 적용하지 않는다. CB1/CB2의 공식 상세 계산식은 **기준 IOPS = max(100, 용량GB × 3)**다. 3,000 버스트는 크레딧 기반의 일시 성능이며 지속 성능 예산으로 사용하지 않는다. 실제 성능은 볼륨과 서버 제한 중 작은 값에 영향을 받는다. [Ncloud 스토리지 성능 상세](https://guide.ncloud-docs.com/docs/server-storage-vpc)

| 신규 CB SSD 크기 | 기준 IOPS | 선택 판단 |
|---|---:|---|
| 50GB | 150 | 수집 증가와 보관 장애에 대한 여유 부족 |
| 100GB | 300 | 정상 소량 수집 시작 가능성이 있으나 매매·급증 여유 부족 |
| 200GB | 600 | 보관 용량은 충족; 성능은 실부하 시험으로 판단 |
| 300GB | 900 | 경제적인 시작안; 3종목·순차 확장·원격 보관 조건 |
| **500GB** | **1,500** | **6거래소·단기 급증·실시간 매매를 위한 권장안** |

측정된 포화 처리량을 기준점으로만 사용하면 거래소 2배·단기 유입 5배·30% I/O 여유의 거친 설계값은 `103 × 2 × 5 ÷ 0.70 ≈ 1,470 IOPS`다. 500GB의 기준 1,500 IOPS가 이 예산과 맞는다. 기존 Market 부하는 거래소 수와 비례하지 않고 NATS/SQLite 배치도 달라지므로 이 계산은 피크 수요의 측정이나 처리 보장이 아니다. 신규 볼륨에서 실제 워크로드를 검증한 뒤 성능 여유를 판정해야 한다.

현재 High CPU 2 vCPU/4GB 모델의 문서상 서버 IOPS QoS 최대는 5,250이고, 4 vCPU/8GB는 7,875다. 500GB CB의 기준 1,500 IOPS는 그보다 낮으므로, 용량 증설로 서버의 IOPS 상한을 바로 넘는 상황은 아니다. [Ncloud 서버 성능 QoS](https://guide.ncloud-docs.com/docs/server-spec-vpc)

## 디스크 배치와 실시간 매매

| 디스크 | 권장 용도 |
|---|---|
| 기존 10GB | OS·제한된 시스템 로그; 코인 DB는 신규 볼륨으로 이동 |
| 기존 20GB | 기존 Market/SK 데이터·기존 내보내기 파일 |
| 신규 300GB CB | NATS JetStream 전체 저장 디렉터리, 기준 900 IOPS |
| 신규 200GB CB | 코인 SQLite/WAL·Parquet·원격 업로드 임시 파일, 기준 600 IOPS |

두 개가 번거로우면 신규 500GB 하나에 NATS와 코인 상태·Parquet를 배치한다. 디렉터리나 파티션만 나누는 것은 물리 I/O 격리가 아니다. 현재 NATS는 전체 인스턴스의 저장 디렉터리를 공유하므로 단순히 코인 스트림 설정만 바꿔 파일을 다른 디스크에 옮길 수 없다. 인스턴스 전체 store_dir를 새 볼륨으로 이동하거나, 별도 코인 NATS 인스턴스를 설계해야 한다.

새 디스크를 빈 채로 붙이면 기존 20GB의 쓰기 지연은 그대로다. 데이터를 검증해서 실제 활성 저장 경로를 이동하고, 컨테이너 마운트·권한·systemd 시작 순서를 일치시켜야 한다. 기존 SK 데이터는 삭제 대상이 아니다.

코인 NATS 스트림 상한은 현재 128MiB다. 저장이 완전히 멈추면 6거래소 예상 내부 유입 0.87MB/s에서 약 2.6분, 5배 유입에서 약 31초 분량이며 실제 pause는 설정 임계값에서 더 빨리 발생한다. 새 디스크 도입 시 코인 스트림을 **1~2GiB**, NATS 전체 파일 예산을 **4GiB 이상**으로 재설계하는 것이 적절하다. 2GiB는 예상 정상 유입 약 41분, 5배 유입 약 8분의 명목 큐다. 큰 큐는 장시간 처리능력 부족을 해결하지 않고 잠깐의 지연을 흡수한다.

현재 코드에서 `NatsJetStreamBus.publish_market_event()`는 JetStream 발행 ACK를 기다린 뒤 `live.crypto`로 전달한다. 전략은 메모리 호가를 읽지만 전달 자체가 NATS 저장 지연의 영향을 받을 수 있다. 주문 의도도 DB 기록과 버스 발행을 거친다. 디스크 여유와 별개로 수신→전략→주문 ACK의 p95/p99, WebSocket 재연결 후 호가 재동기화, 비공개 주문/체결 스트림의 복구를 점검해야 한다. 이 산정 작업에서 실제 주문은 실행하지 않았다.

기존 2 vCPU·4GB에서 거래소 3개를 더 추가하고 전략까지 돌리는 구성은 메모리·단기 CPU 여유가 작다. **4 vCPU·8GB를 운영 시작 권장치**로 잡고, 여러 전략·깊은 호가·백테스트 병행이면 16GB를 검토한다. 스토리지만 추가하면 RAM·압축 CPU·네트워크 왕복 지연은 개선되지 않는다.

## 확장 후 확인 조건

먼저 저장 경로를 이동하고 기존 3거래소로 부하를 비교한다. 이후 거래소를 하나씩 추가해 같은 호가 설정에서 정상·3배·5배 입력의 격리 재생 시험과 운영 관찰을 한다. 운영 서버에 직접 대량 재생 부하를 넣지 않는다.

버스트 잔량에 기대지 않는 지속 처리, 커밋/ACK 적체의 증가 추세, 업로드 회복, 발행/주문 p95·p99, CPU와 메모리·디스크 여유를 확인한다. 현재의 평균 86ms 쓰기 대기와 I/O PSI full 약 46%가 새 경로에서도 계속되면 목표 처리량 검증을 통과한 것으로 보지 않는다. 승인 가능한 매매 지연 기준은 실제 전략 주기와 대상 거래소 왕복 시간에 맞춰 정해야 한다.
