# 2026-10-15 수집 중단 원인·ETF 분봉 누락 재검증

기준: 2026-10-15 10:28~10:29 KST 서버 읽기 전용 검사. 대상: VibeTrading main 서버 49.50.141.106. 이번 후속 조사에서는 파일 삭제, 서비스 재시작, 토큰 발급, 과거 시세 API 호출, 주문 제출을 하지 않았다. 로컬에 조사 문서와 메타데이터 증적만 작성했다.

## 1. 갑작스러운 디스크 감소를 일으킨 파일

**직접 원인은 루트 디스크에 새로 설치된 VS Code 원격 서버 버전이다.** 불필요한 Python 소스나 latency 측정 결과가 수백 MB씩 갑자기 루트에 쌓여 발생한 현상이 아니다. 정지를 실행한 것은 호스트의 `vibetrading-os-disk-guard.service` → `os-disk-guard.sh` → Docker stop이다.

|---|---:|---|
| 04:33:06 | 1,649,393,664 | 정상 유지 |
| 04:33:17 | 1,649,381,376 | 정상 유지 |

04:33:06 → 04:33:39 감소량은 **702,922,752바이트**다. 그 시각 생성된 버전 `Stable-16507d91be0dc1ce4f94c04d4d0430210b8685d9`의 실제 할당량은 **702,885,888바이트**다. 차이는 36,864바이트뿐이다. 설치 디렉터리의 보존된 mtime은 04:33:30, 하위 디렉터리 생성 완료는 04:33:38로 정지 직전과 일치한다. 이러한 일치는 갑작스러운 사용량 증가의 직접 원인을 뒷받침한다.

루트는 약 10GB이며, 이전 VS Code 서버 세 버전도 합계 약 2.08GB의 할당 공간을 사용하고 있었다. 새 버전이 추가되기 전부터 여유가 약 1.65GB여서 703MB 추가만으로 가드가 작동했다. 사용량이 100%가 된 뒤 파일 쓰기가 실패한 사건이 아니라, **보호용 여유 임계값을 밑돌아 수집기가 선제적으로 정지된 사건**이다. 기존 가드는 여유가 2GiB 이상이어야 재개하므로 장이 열려도 재개되지 않았다.

새 VS Code 버전 설치를 시작한 접속·프로그램 주체는 확보한 SSH/VS Code 기록만으로 특정하지 못했다. 자동 업데이트, 특정 사용자, Codex 작업이 설치를 시작했다고 단정하지 않는다. 장기간 루트 사용량의 모든 증감을 재구성할 과거 디스크 스냅샷도 없다.

### Telegram 작업이 수집기에 미친 변경

이전 Telegram/수집기 장애 대응에서 `runtime.py`의 수집 세션·watchdog 및 NATS publish 관련 공통 경로를 수정했고, 복원 배포에서 수집기 이미지를 재생성한 이력은 있다. 따라서 “Telegram 작업 중 수집기 코드는 전혀 건드리지 않았다”는 설명은 부정확하다.

그러나 이번 04:33 중단은 API 예외·NATS timeout·OOM 종료가 아니라 호스트 가드가 명시적으로 실행한 stop이며, 로그와 디스크 감소량으로 구분된다. Kiwoom 인증 함수가 그 작업에서 삭제되거나 새로 깨졌는지도 아래와 같이 별도로 비교했다.

## 2. Kiwoom의 기존 토큰 갱신이 있었는데도 실패한 이유

**원래 토큰 캐시와 만료 전후 갱신 구조가 있었다.** 10/03, 10/13, 10/14 배포 보관본의 `KiwoomAuthClient.access_token`, `_read_token_cache`, `_write_token_cache` 세 함수의 소스 SHA-256이 각각 모두 동일하다. 10/13 ETF 배포본과 10/14 Telegram 복구 배포본의 `providers/kiwoom.py` 전체 SHA-256도 `6dce3d32140f5425c0abf453b681ba05f8c9ac1dc476ba003af34d5244bbd4d4`로 동일하다. 기존 이미지 네 버전의 소스도 같은 전체 해시였다.

10/03 → 10/13에는 ETF REST 분봉 폴링과 WebSocket을 함께 실행하는 수집 구조가 추가됐다. 하지만 인증 세 함수는 그대로였다. 동시 접근에 대한 방어가 부족했던 사실과, 동시 발급이 오늘 토큰을 무효화했다는 주장은 다르다. **후자는 입증되지 않았다.**

관측된 실패는 다음 두 단계다.

1. 04:33~복구 시점: KIS·Kiwoom·TOSS 공용 프로세스 자체가 정지했다. 이 기간 미수집의 직접 원인은 디스크 가드다.
2. 디스크 복구 후 약 09:58 재접속: KIS·TOSS는 재개됐지만 Kiwoom은 REST `return_code=3`/본문 `8005`, WS `805004`로 토큰을 거절했다. 캐시의 표시 만료는 `20261016095857`로 미래였고, 기존 코드는 만료 시각만 보고 거절된 토큰을 계속 재사용했다. 만료를 기준으로 한 기존 갱신만으로는 이 상태를 벗어나지 못했다.

현재 `/root/vibetrading/.env`, `/etc/vibetrading/app.env`, 실제 collectors 컨테이너의 **효과적인** Kiwoom 앱키·시크릿·모의 여부는 값 노출 없이 비교했으며 모두 존재하고 일치했다. 시크릿은 기존 `KIWOON_APP_SECRET` 별칭도 포함해 비교했다. 이 결과는 현재 설정 일치만 증명하며, 거절된 옛 토큰이 어떤 자격증명으로 언제 발급됐는지까지 증명하지 않는다.

최초 거절된 토큰 원본과 발급 주체 이력이 보존되지 않았고 공급자의 무효화 감사 기록도 없다. 따라서 **그 토큰이 처음 왜 무효가 됐는지는 현 증거로 확정할 수 없다.** 재발급에 따른 폐기, 자격증명 교체, 키움 측 무효화 등을 원인으로 단정하지 않는다. 이 저장소에서 명시적 토큰 revoke API를 호출하는 구현도 찾지 못했다.

오늘 복구에서 추가한 것은 인증 거절 시 해당 캐시만 무효화하고 조회 API를 새 토큰으로 한 번 복구하는 경로, 자격증명 fingerprint, 프로세스 간 잠금이다. 자동 주문 재전송을 추가한 것은 아니다. “만료 갱신이 없어서 새로 구현했다”가 아니라 **기존 만료 갱신에 인증 거절 복구를 보완했다**는 것이 정확하다. 키움 공식 예제도 캐시 유효성 검사와 인증 실패 복구를 별도 경로로 다룬다. [공식 인증 구현](https://github.com/Kiwoom-Securities/Kiwoom-REST-API/blob/main/kiwoom/core/auth.py), [공식 오류 분류](https://github.com/Kiwoom-Securities/Kiwoom-REST-API/blob/main/kiwoom/core/errors.py).

## 3. ETF 분봉은 현재 어디까지 복구됐는가

10:28~10:29에 서버의 기존 세션 JSONL만 읽어 **중단 구간 분봉 종료 시각 09:01~10:08, 총 68개 슬롯**을 검사했다. broker history API나 무거운 복구 작업을 새로 실행하지 않았다.

| 티커 | 중단 구간 저장 슬롯 | 없는 종료 시각 | 저장된 첫 종료 시각 | 조사 당시 최신 종료 시각 |
|---|---:|---|---|---|
| 069500 KODEX 200 | 68 / 68 | 없음 | 09:01 | 10:27 |
| 122630 KODEX 레버리지 | 66 / 68 | **09:01, 09:02** | 09:03 | 10:28 |
| 229200 KODEX 코스닥150 | 68 / 68 | 없음 | 09:01 | 10:27 |
| 251340 KODEX 코스닥150선물인버스 | 68 / 68 | 없음 | 09:01 | 10:28 |

저장 시각은 KST의 **bar_end**다. 빠진 두 슬롯은 원시 분봉 시작 시각으로 09:00·09:01에 해당한다. 개장 지연·무거래여서 원본에 없었는지, 실제 거래 분봉이 누락됐는지는 저장 데이터만으로 확정하지 못했다. 빈 슬롯을 전일 종가나 거래량 0으로 만들어 넣지는 않았다.

분봉 전체가 계속 빈 상태는 아니다. 앞선 복구 과정의 REST backfill로 세 ETF의 중단 구간 슬롯은 채워졌다. 다만 122630의 두 슬롯이 없으므로 “네 ETF 전체 복구 완료”라고 표현한 이전 설명은 정정한다. 이 검사는 슬롯 존재 확인이며, 각 OHLCV 값을 거래소 원본과 모두 대조한 품질 검증은 아니다.

세션 파일에는 반복 조회로 같은 시각의 행이 여러 번 기록된다. `EtfCsvSync.captured()`는 timestamp별 마지막 행을 사용한다. 069500의 10:09·10:13, 229200의 10:19에는 값이 다른 revision도 있었다. 이 JSONL은 단순 중복 백업 파일로 분류하지 않는다. 장마감 REST 스냅샷은 같은 시각의 캡처 값을 덮어 최종 CSV에 병합한다.

### CSV에 오늘 행이 아직 없는 것의 의미

서버 과거 데이터 위치는 `/srv/vibetrading-data/runtime_data/state/etf-mock/history/raw/`다. 장중 캡처는 `/srv/vibetrading-data/runtime_data/state/etf-csv-sync/sessions/2026-10-15-티커.jsonl`에 쌓인다. 과거 CSV와 manifest의 최종 일자는 네 ETF 분봉·일봉과 두 지수 일봉 모두 2026-10-14다. 이는 기존의 장마감 후 CSV 추가 설계와 일치하며, 오늘 데이터가 전부 사라졌다는 뜻이 아니다.

국내 CSV 갱신은 장마감 후 5분 유예를 두고 수행하고 S&P500은 미국 세션 마감이 확인된 일자까지만 추가한다. 현재 키 이름과 파일명은 `KOSPI200_daily`다. KOSPI 종합지수 파일과 혼동하면 안 된다.

복구한 과거 분봉은 지표 입력을 복원하지만, 당시 실시간 호가·체결 스트림과 놓친 주문 기회를 복원하지 못한다. C3 개장 구간 및 KP/KD 평가 시점이 지나갔다고 과거 신호 주문을 현재 제출하지 않는다.

## 4. 로컬에서 수집한 누락분을 서버에 추가할 수 있는가

**가능하다. 서버에서 broker backfill을 다시 실행할 필요는 없다.** NATS만이 유일한 영구 저장소인 구조도 아니다. NATS는 전송·재생 구간이고 storage worker가 별도 Parquet와 원격 저장소로 저장한다. ETF 전략에는 위의 과거 CSV와 장중 세션 파일·메모리 입력이 추가로 있다.

권장 경로는 로컬에서 누락 티커·시간 범위만 수집 → 검증된 파일을 별도 staging에 업로드 → 대상 계층에 제한적으로 병합하는 것이다. 파일 전송 자체는 수집기나 NATS의 재시작을 요구하지 않는다. 다만 **누락분 CSV를 아무 경로에 복사하면 자동 반영되는 완성된 외부 import 명령은 현재 없다.** 기존 `import_future_trading_csv.py`는 최초 과거 묶음 패키징용이다.

| 반영 목적 | 필요한 처리 | 현재 제약 |
|---|---|---|
| 오늘 분봉을 장마감 기록에 보존 | 검증된 행을 세션 데이터에 병합하거나 마감 CSV writer 입력으로 제공 | 수집 중인 JSONL을 임의 덮어쓰면 안 됨; 단일 writer·중복키 처리 필요 |
| 실행 중 전략의 오늘 입력에도 반영 | 현재 이벤트 스키마에 맞는 BAR_1M을 `ingest_mode=backfill`로 발행 | 직접 세션 파일 편집만으로 실행 중 메모리는 갱신되지 않음; importer 구현 필요 |
| 이미 CSV에 마감 일자가 기록된 날짜의 내부 구멍 복구 | 잠금 안에서 원자적 파일 교체, manifest 행 수·SHA-256·범위 갱신 | 기존 `append_closed()`는 watermark 이하 날짜를 무시하므로 별도 repair 경로 필요 |
| 오래된 전체 과거 이력 | CSV 계층에서 검증·병합 | NATS 이벤트 최대 연령 기본 172800초 때문에 오래된 전체 CSV를 그대로 재생하면 안 됨 |

검증 항목은 티커 문자열의 앞자리 0 유지, KST와 bar_start/bar_end 변환, 완료 분봉만 사용, OHLC 관계·양수 가격·비음수 거래량, timestamp 중복·기존 값 충돌, 예상 슬롯 및 원본 해시다. importer는 실제 새 분봉처럼 신호를 내지 않도록 **모든 복구 행을 명시적으로 backfill 처리**해야 한다. 현재 `EtfTradingLoop.on_event()`는 backfill의 분봉 입력은 반영하되 주문 평가를 생략한다. 최근 2분 이내 시각이라도 외부 복구 행을 realtime으로 지정하면 안 된다.

이번 요청은 가능 여부와 위험 분석이므로 importer를 새로 배포하거나 데이터를 주입하지 않았다. 같은 자격증명을 쓰는 로컬 수집이 서버의 토큰·허용 IP 정책과 충돌하지 않는지도 별도 확인해야 하며, 서버 캐시 파일을 로컬에서 공동 편집하지 않는 방식이 적절하다.
