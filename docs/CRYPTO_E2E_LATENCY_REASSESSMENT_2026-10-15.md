# 코인 E2E 지연 비교 재분석 — 2026-10-15

기존 집계에서 서로 다른 이벤트 종류를 같은 네트워크 지연처럼 비교한 것은 부정확했다. 계측의 시계/수신 지점/계산식은 같지만, Arcus 438.898ms는 체결 78건, GRVT 24.699ms는 호가 3241건이다. Binance 혼합값 22.367ms도 호가와 체결을 섞은 값이다.

## Arcus 추가 확인

운영 수집기 설정 변경과 주문 제출 없이 서버에서 독립 공개 WS 연결로 두 차례 약 35초씩 관측했다. 같은 트레이드 ID로 운영 live NATS 이벤트를 매칭했다. private 계정은 사용하지 않았다.

| 실행 KST | 직접 체결 n | 이벤트→직접 수신 p50/p95 ms | ping RTT p50 ms | 운영 live − 직접 수신 p50/p95 ms |
|---|---:|---:|---:|---:|
| 10-15 00:26:57 | 44 | 22.473/52.233 | 30.601 | 66.381/258.249 |
| 10-15 00:28:35 | 55 | 26.771/29.351 | 38.484 | 6.915/195.535 |

두 번째 대조 55건은 source timestamp도 모두 일치했다. 운영 receive_ts_ns는 파싱 중 찍히는 시각이므로, 이것과 직접 WS 수신 시각의 차이를 보면 운영 파싱 전 추가 지연 p50 0.644ms/p95 161.041ms/최대 325.373ms가 관측된다. 이후 파싱→live p50은 6.271ms/p95 35.660ms였다. 서로 다른 WS 연결/게이트웨이 차이도 포함하므로 전부 Python 큐 지연으로 단정하지 않는다.

따라서 438.898ms는 Arcus의 정상 네트워크 편도 지연으로 사용할 수 없다. 당시의 늦은 체결 전달/수집기 backpressure·미수신 대기/스케줄링 등이 섞였을 가능성이 크다. 이전 실험에는 독립 연결 동시 대조가 없어 그 438.898ms 전체의 원인을 확정할 수는 없다. 직접 피드에서도 exchange clock은 보정하지 않았으므로 RTT/2와 같은 지표라고 해석하지 않는다.

## 같은 종류로 분리한 기존 표본

정규화→publish 진입은 정책 처리·직렬화·publisher 큐·스케줄링 대기를 포함한다. 이를 순수 NATS 서버 처리 시간으로 부르면 안 된다. 아래는 모두 p50, ms.

| 거래소/종류 | n | 정규화→publish 진입 | publish 함수 | publish 완료→live | 정규화→live |
|---|---:|---:|---:|---:|---:|
| binance-perp/order_book | 738 | 0.183 | 2.208 | 0.694 | 3.924 |
| binance-perp/trade | 2031 | 9.678 | 0.926 | 0.685 | 12.525 |
| arcus-perp/order_book | 20380 | 18.876 | 0.766 | 0.591 | 20.729 |
| arcus-perp/trade | 78 | 22.825 | 0.765 | 0.605 | 24.546 |
| grvt-perp/order_book | 3241 | 0.494 | 1.620 | 0.676 | 3.780 |

각 구간의 p50을 합하면 전체 p50과 반드시 일치하는 것은 아니다. Binance 호가와 GRVT 호가는 3.924ms 대 3.780ms로 유사하다. Binance 혼합값 7.518ms는 73%가 상대적으로 지연된 체결 표본인 결과이기도 하다.

서버 실제 실행 중인 BufferedMarketEventBus도 기본 shards=4이며 종목키 SHA256 %4로 배정함을 확인했다. Binance BTC/ETH/SOL은 모두 shard 2에 충돌한다. Arcus BTC/SOL은 0, ETH는 1이고, GRVT BTC/ETH는 2, SOL은 3이다. 동일한 코드도 실제 병렬성은 다르다. 동일 종목의 호가/체결은 같은 큐에서 순서를 유지하므로 체결 버스트가 다른 이벤트 대기를 늘릴 수 있다.

관측 live 유입량은 Arcus 102288건, Binance 13844건, GRVT 3241건이다. Arcus는 GRVT의 약 31.6배다. Arcus publish 함수 자체는 오히려 빠르지만 호출 전 대기가 18.876ms로 높다. 서버 2 vCPU에 다른 서비스도 같이 실행 중이므로 부하·큐 분포·메시지 수와 크기·스케줄링이 영향을 준다. 큐 배정 문제를 발견했으나 이번 질문은 설명과 계산이므로 운영 코드 변경/재배포는 하지 않았다.

## 요청한 주문 구간 proxy 계산

L_i = 정상화한 이벤트→수신 대표값, S_i = 수신→의도 대표값, G = GRVT의 24.6985ms, r_i = L_i/G로 둔다. GRVT IOC 주문 20건의 A_j = 의도 완료→WS send, F_j = WS send→첫 fill 통보를 사용한다. 같은 주문 내 A/F 쌍을 보존했다. median(A+F)는 102.9772ms이다.

- 주문 구간 전체를 비례시키는 해석: E_i = L_i + S_i + median_j[r_i × (A_j + F_j)].
- 로컬 비용을 고정하는 해석: E_i = L_i + S_i + median_j[A_j + r_i × F_j].

서명·증적 fsync 등 로컬 비용 A까지 통신 지연에 비례한다고 보기 어렵기 때문에 두 번째 모델을 권한다. 그러나 F에는 testnet 매칭/리스크 검사/통보 배치도 섞여 있으므로 그 비례성 역시 사용자 가정에 따른 proxy다. G는 운영 GRVT ingress, F는 testnet 실행 구간이므로 물리적 네트워크 캘리브레이션이 아니다.

| 시나리오 | L ms | S ms | 주문 전체 비례 E ms | 로컬 비용 고정 E ms |
|---|---:|---:|---:|---:|
| Binance book | 17.528 | 4.511 | 95.118 | 107.018 |
| Binance mixed | 22.367 | 8.222 | 123.846 | 127.716 |
| Arcus normal 22.4725 | 22.473 | 20.860 | 137.029 | 140.724 |
| Arcus normal 25 | 25.000 | 20.860 | 150.095 | 149.535 |
| Arcus normal 26.771 | 26.771 | 20.860 | 159.250 | 155.403 |

Arcus의 25ms는 새 직접 체결 피드에서 관측한 22.5~26.8ms를 참고한 가정이다. Arcus 증분 호가는 timestamp가 없으므로 호가 자체의 25ms를 검증한 결과는 아니다. S는 기존 호가 표본의 값을 그대로 유지해 수집기 최적화까지 가정하지 않는다.

이 값은 L/S 대표값과 주문 구간 proxy를 조합한 시나리오이며 실측 E2E p50/p95가 아니다. GRVT에서도 이 대표값 조합은 131.750ms지만 실제 주문별 연결 E2E 중앙값은 139.442ms였다. 이 차이를 고려해 추정값을 소수점 단위 정확도로 해석하지 않는다. p95는 이 표로 추정하지 않는다.

직전 측정은 시장가 자체가 아니라 20 bps 범위의 즉시 체결 IOC 지정가였다. 유동성이 충분하고 즉시 체결된다는 가정에서 시장가의 proxy로 사용한다. ACK는 submit→fill 구간 안에 포함되므로 별도로 더하지 않는다. 실제 전략 계산/리스크 검증 시간은 측정되지 않았으며, 추가되면 E2E도 늘어난다.


## 10% 이상 개선만 인정하는 코드 변경 기준

200ms 이하는 정상 수신·즉시 체결·측정용 즉시 의도라는 기존 가정 아래의 시나리오 판단이다. 세 거래소 실제 전략의 운영 E2E 중앙값이 모두 검증되었다는 뜻은 아니다. 기준값은 Binance 호가 약 107ms(추정), Arcus 정상 ingress 약 150ms(추정), GRVT 약 139ms(testnet 실측)다. 10% 목표 절감은 각각 약 11/15/14ms다.

시세 처리 대표값에서 Binance와 GRVT의 수신→의도는 각각 약 4.5/4.1ms이므로 해당 구간 개선만으로 10% 효과를 기대할 근거가 부족하다. Arcus는 약 20.9ms이므로 저장과 전략 시세 전달의 임계 경로를 분리할 후보가 있다. 현재는 정규화→저장 publisher 큐→JetStream ACK→live 순서다. 검토할 구조는 검증된 시세→live/의도와 별도의 durable 저장 경로를 나누는 것이다. 단순히 같은 큐 안에서 ACK와 live 순서만 바꾸는 것으로는 reader backpressure가 해소되지 않는다.

Arcus의 수신→의도를 3~5ms로 낮추면 대표값 예산에서 15.9~17.9ms, E2E 약 10.6~11.9% 절감이 목표다. 이는 설계 목표이며 달성 실측이 아니다. 저장 경로 지연/장애 시 수집 지속·메모리 상한·주문 허용 여부와 호가 순서/재동기화 정책도 함께 설계해야 한다. 현재 Arcus 438.9ms 같은 비정상 입력 지연을 정상화하는 효과를 여기서 다시 중복 산입하지 않았다.

GRVT 계측의 의도→제출에는 두 차례 전체 증적 JSON fsync와 기타 dispatch 비용이 포함됐다. 서명 제외 제출 전 부가 비용 중앙값은 15.199ms다. 이 전부가 fsync의 순수 시간인 것은 아니며, 측정기 비용 제거는 운영 시스템 성능 개선 실적으로 세지 않는다.

서명 최적화의 크기를 확인하기 위해 운영 계좌/키/네트워크 없이 동일 서버 이미지에서 고정 테스트 키로 prepare_order를 각 50회 측정했다. 현재 NativeECCBackend는 중앙값 4.980ms, Account 객체만 캐시한 경우 3.538ms로 약 1.442ms 감소했다. 기존 부하 중 기록된 17.508ms에서 4.980ms로 줄었다는 A/B 개선 실험이 아니며 조건이 다르다. 객체 캐시는 사용자 기준에 따라 제외한다. 네이티브 서명 백엔드나 전면 언어 변경으로 10% E2E 개선을 보였다는 자료도 없다.

현재 증거로는 Arcus의 저장/실시간 전달 분리만 10% 이상 개선 후보로 남기며, 확정 효과로 제시하지 않는다. Binance 샤드 충돌 해소는 긴 지연 완화 후보지만 정상 E2E 중앙값 10% 개선은 검증되지 않았다. 동일 부하의 변경 전후 비교에서 전체 E2E 중앙값 10% 이상 감소를 확인하기 전에는 경제적 가치가 확인된 변경으로 분류하지 않는다.
