# 코인 수집 장애 진단 문서 평가 및 수정안

작성: 2026-09-28 KST. 첨부 `vibetrading_crypto_backpressure_final_analysis.md`를 보존된 측정 자료, 작업 소스, 운영 컨테이너와 대조했다. 이번 작업은 읽기 전용 서버 조사와 문서 작성만 수행했다. 코드·설정·데이터 삭제·재시작·부하 시험은 수행하지 않았다.

## 1. 평가 결론

첨부 문서의 방향은 대체로 타당하다. **공유 디스크의 I/O 경합, NATS 상태 조회 실패의 부정확한 분류, 6GiB 재개 조건**은 실제 문제다. 다만 최초 중단 원인을 `STREAM.INFO` 타임아웃으로 우선 단정하거나, 공통 프레임워크·전역 컨트롤러 도입을 I/O 개선보다 앞세우는 것은 수정해야 한다.

추가로 확인한 핵심 누락은 **주식 maintenance의 시간당 전체 SQLite 백업이 운영 서버에 그대로 남아 있다는 점**이다. 코인 쪽만 하루 1회 백업으로 바뀌었다. 프로세스와 SQLite를 분리해도 같은 디스크를 쓰므로 주식 백업이 코인 수집의 중단 조건을 만들 수 있다.

현재 근거로 가능한 판정은 다음과 같다.

| 질문 | 판정 |
|---|---|
| RAM 부족이 이번 중단의 직접 원인인가? | 확인되지 않았다. 앞선 17:14 측정에서 가용 약 1.60GiB, 메모리 PSI 0이었다. 코인 storage는 메모리 한도 내에 있다. |
| 디스크 저장공간이 완전히 소진됐는가? | 아니다. 다만 유지보수 중 일시 여유 공간이 4GiB 중단 기준 아래로 내려갔다. |
| 디스크 I/O 병목은 실재하는가? | 그렇다. 높은 PSI, 지연, 대기열과 I/O 증가가 관측됐다. |
| 코인 원본 유입 자체가 서버의 지속 처리 능력을 넘는가? | 아직 입증되지 않았다. 정상 수집 구간과 유지보수 부하를 분리한 전체 경로 시험이 없다. |
| 저장·복구 구조에 비효율이 남았는가? | 그렇다. 시간당 주식 DB 백업, 신규 이벤트 DB 조회, 원장 전체 건수 조회, 삭제 작업의 처리율·I/O 제어 문제가 남아 있다. |
| 증설만 하면 해결되는가? | 아니다. 중단·재개 판단과 유지보수 문제는 증설 후에도 재발 가능하다. |

### 주식 maintenance의 백업과 디스크 급감

- 같은 컨테이너 `860a68addfa5`의 Block I/O가 16:26~16:29에 읽기 **144→151GB**, 쓰기 **49.5→51.9GB**로 증가했다. 누적값 자체가 아니라 동일 컨테이너의 시간차를 비교한 것이며 표시값 반올림 오차가 있다.
- 주식 DB `archive_backup.created_ts_ns`에 **16:26:26** 백업 시작 시각이 등록돼 있다. 실행 코드는 시작 시각을 저장하므로 완료 시각으로 해석하면 안 된다.
- 이후 백업 시작 시각은 **17:29:29, 18:31:34, 19:33:13, 20:34:23**이다. 실제 시간당 실행이 확인된다.
- 주식 maintenance의 실행 소스는 기본 백업 간격 **3,600초**, 부하 검사 없이 전체 DB 임시 사본을 만들고 업로드한다. `put_file` 뒤 별도 `verify` 호출도 남아 있다. 별도 verify의 추가 네트워크 비용은 해당 실행 backend까지 대조해야 확정할 수 있다.
- 반면 코인 maintenance에는 **86,400초** 설정과 부하 검사가 적용돼 있다.

따라서 16:27~16:28의 대규모 임시 공간 점유와 I/O 증가는 **주식 DB 백업과 강하게 연결된다.** 파일별 생성·삭제 로그가 없어 모든 공간 변화를 백업 하나에 정확히 배분할 수는 없다. 같은 시간의 replay 영향 역시 완전히 배제하지 않는다.

- Binance·Bitget·Bybit 모두 `phase=paused`, `reason=storage_or_nats_backpressure`.
- `CRYPTO_DATA`: 메시지·바이트·pending·ack_pending·redelivered 모두 0. ACK floor와 delivered stream sequence 모두 **6,477,246**.
- 마지막 코인 스트림 이벤트 시각 **17:02:24.765 KST**. 17:03 이후 자료는 정상 수집 성능 표본으로 사용할 수 없다.
- 코인 storage: messages=acked=**1,063,458**, pending=0, buffer=0. RSS 약 367MiB, cgroup 한도 768MiB.
- 디스크 여유 **6,402,736,128 bytes ≈ 5.963GiB**, 재개 기준 6GiB보다 약 37.9MiB 부족.

- 코인 `storage_worker.py`, `sqlite_store.py`, `archive.py`는 로컬 소스와 운영 컨테이너의 SHA-256이 일치했다. 아래 코드 지적은 실제 배포에 해당한다.

## 3. 오류 원인 수정

### A. 16:28 중단: 실제 디스크 임계치 진입 증거가 있다

여유 3.715GiB는 코드의 `free_bytes <= 4GiB` 중단 조건을 충족한다. 같은 표본의 NATS는 약 3.55MiB다. 따라서 이 구간은 NATS 80% 적체나 상태 조회 타임아웃을 가정하지 않아도 중단을 설명할 수 있다. 정확히 어떤 조건이 첫 예외를 발생시켰는지는 상세 원인 로그가 없어 구분할 수 없다.

### B. 17:02경 재중단: 최초 트리거는 여전히 미확정

직전 표본에서 디스크 여유는 4GiB보다 높고 NATS 사용량도 낮다. 가능성은 상태 조회 실패, 발행 타임아웃, 짧은 적체·공간 피크, publisher 실패 등이다. `STREAM.INFO` 예외를 1.0으로 처리하는 코드는 확인됐지만, **그 예외가 이 시점에 발생했다는 로그는 확보하지 못했다.** 첨부 문서의 A/B 두 시나리오만으로 원인을 제한하면 안 된다.

또한 17:10 이후 높은 PSI를 17:02 중단의 직접 증거로 소급 적용하면 안 된다.

### C. 중단 후 장시간 미복구: 재개 조건 미달이 직접 확인된다

현재는 디스크가 비어 있거나 사용률이 낮아졌다는 사실만으로 복구되지 않는다. `used_ratio < 75%`, `free >= 6GiB`, `stream_ratio < 50%`, 안정화 시간을 모두 만족해야 한다. 현재 free 조건이 실패하므로 NATS가 비어도 latch가 해제되지 않는다.

이는 의도된 히스테리시스가 현재 운영 공간 예산과 맞지 않는 문제다. 임계치 자체를 없애거나 재시작으로 latch를 초기화하면 원인만 가려진다.

### D. 수집 정지 후에도 유지보수 I/O가 남는다

17:07~17:13에는 코인 NATS가 계속 0인데 코인 maintenance 누적 쓰기가 약 **10.1→242MB**로 증가했고 PSI도 상승했다. 코인 storage의 쓰기 계수도 증가했다. 삭제·체크포인트 등 저장 후속 작업이 조사 대상이다. 이 자료만으로 모든 쓰기를 prune 하나에 귀속시키지는 않는다.

## 4. 첨부 개선안에서 수정할 부분

| 원안 | 평가와 수정 |

| 조회 예외를 용량 100%와 구분 | 타당. `unknown/degraded`와 실제 용량 초과를 구분한다. 보호 목적의 수집 중단은 여전히 허용해야 한다. |
| 60초 캐시 사용, timeout 시 즉시 pause 금지 | 조건부 타당. 마지막 낮은 값만 믿으면 실제 용량 초과를 놓칠 수 있다. 캐시 나이, 남은 바이트, 유입 속도, 발행 실패·큐 압박을 함께 제한한다. 초기값 없음·만료·재연결/스트림 세대 변경 시 fail-closed 처리가 필요하다. |

| Market 구현을 안정적인 기준으로 채택 | 수정 필요. 운영 Market maintenance에는 시간당 백업이 남아 있다. Market의 캐시도 60초 후 실패 시 1.0을 반환한다. 그대로 복제하지 않는다. |
| I/O 개선을 Phase 4/P2로 배치 | **P0~P1로 올린다.** 주식 백업과 공유 디스크 부하를 남겨 둔 채 코인 재개만 고치면 재발한다. |
| 디스크 임계치를 비율에 맞춰 축소 | 비율만으로 정하지 않는다. DB 백업·WAL·NATS·flush·복구 임시 공간의 동시 최대량을 확보해야 한다. |
| 텔레그램에 모든 지표 출력 | 내부 로그에는 모두 기록하되 알림은 원인·영향·핵심 수치 2~3개로 제한한다. 짧고 읽기 쉬운 status를 원하는 기존 요구를 유지한다. |
| 커밋 태그로 배포 출처 보장 | 방향은 타당. dirty source·의존성·base image도 반영하고 실행 digest를 기록해야 한다. git SHA 태그만으로 완전한 재현성이 보장되지는 않는다. |

`CRYPTO_NATS_MAX_BYTES` 환경값만 분모로 쓰지 말고 실제 서버 stream 설정과도 대조해야 한다. 둘이 다르면 probe가 정상이어도 사용률 판단이 틀릴 수 있다.

## 5. 문서에서 빠진 저장 구조 개선 항목

1. **신규 이벤트도 DB 중복 조회를 수행한다.** `storage_worker.py:149`의 `candidate_event_ids`에 신규 배치가 포함되고, `committed_event_ids()`가 해시 인덱스를 조회한다. 재전달 delivery 키 조회만 줄었을 뿐 정상 경로의 SQLite 조회가 사라지지 않았다. 다만 첫 delivery라도 같은 event_id가 다른 NATS 순번으로 다시 발행될 수 있으므로 조회를 무조건 제거하면 안 된다. 재발행·재시작·세대 변경까지 포함한 중복 방지 범위를 먼저 정의한다.
2. **maintenance마다 원장 전체 건수를 조회한다.** `archive.py:78` → `delivery_ledger_stats()` → `SELECT COUNT(*)`. 삭제를 부하 때문에 보류한 cycle에서도 실행된다. 이 SQL 경로는 확인됐으며, 실제 캐시 miss와 I/O 기여율은 별도 측정 대상이다. 저빈도 집계나 트랜잭션과 함께 관리하는 계수로 대체할지 검토한다.
3. **24시간 보존만으로 크기 상한이 생기지 않는다.** 삭제 처리율이 만료 유입률을 따라가야 한다. 8,192행/30초는 작업 시간이 0인 경우에도 약 273행/초이고, 실제로는 작업 시간·5분 대기·부하 보류가 추가된다. 초기 관측 266건/초와 비교해도 여유가 작다. 만료 행 유입률, 실제 삭제율, 가장 오래된 안전 삭제 대상의 나이를 관측해야 한다.
4. **삭제 전 PSI 검사만으로 실행 중 I/O를 제한할 수 없다.** 정적 행 수 대신 실제 트랜잭션 시간·WAL 증가량에 따른 작은 배치와 양보를 검토한다. 시장·코인 유지보수의 동시 실행 예산도 필요하다. ACK·원격 검증·24시간 안전 조건은 유지한다.
5. **DELETE는 DB 파일의 OS 크기 감소를 보장하지 않는다.** 내부 재사용 공간과 파일 크기를 따로 관리한다. 주기적 전체 VACUUM으로 해결하려 하면 다시 큰 임시 공간·I/O가 필요하므로 일상 작업으로 넣지 않는다.
6. **컨테이너 분리는 디스크 격리가 아니다.** 기존 stream·DB·worker 분리는 유지한다. 유지보수량 제어 후에도 I/O가 부족하면 Ncloud 볼륨 유형·실효 IOPS·throughput·동시 부하를 확인해 별도 볼륨 또는 성능 상향을 결정한다.

## 6. 수정된 실행 우선순위 — 이번에는 실행하지 않음

### P0: 원인 관측과 공유 디스크 부하 통제

- 중단 당시 probe 성공 여부/나이, 실제 stream bytes/max, free bytes, publish 예외, 큐 건수·바이트를 한 시각축으로 기록하도록 설계한다.
- 주식·코인 두 maintenance의 실제 배포를 모두 점검한다. 전체 백업은 하루 1회·낮은 부하·충분한 임시 공간을 조건으로 하며 동시에 실행하지 않도록 한다.
- 보관 원본을 임의 삭제하지 않는다. 검증된 회수 대상과 롤백 자료의 보존 필요성을 확인해 공간 예산을 마련한다. 현 6GiB 기준을 수십 MiB만 넘기는 방식으로 운영 복구를 설계하지 않는다.
- 캐시·unknown·발행 실패를 분리한 pressure 정책과 reason별 재개 조건을 설계한다. fresh 상태 확인과 안정화 구간을 통과한 뒤 거래소를 순차 재개한다.

### P1: 지속 처리량과 원장 유지 비용 개선

- 신규 이벤트 중복 조회, 전체 COUNT, 원장 삭제, checkpoint, Parquet 파일 크기와 업로드의 비용을 각각 계측해 줄인다.
- 24시간 이후 삭제 처리량이 실제 만료 유입량을 초과하는지 확인한다. 충분한 재사용 공간과 임시 공간을 함께 계산한다.
- liveness/readiness와 실제 종목별 데이터 최신성을 분리한다. paused·장기 connecting은 수집 정상으로 표시하지 않는다.
- 운영 패치를 검증된 소스로 통합하고, 구성과 역할별 실행 digest를 고정한다.

### P2: 검증 결과에 따른 하드웨어·코드 구조 정리

- 동일한 데이터와 유지보수 조건에서 개선 전후 처리량을 비교한다. 필요한 write IOPS·read IOPS·throughput·지연과 여유 용량을 산출한다.
- 최적화 후에도 지속 적체나 높은 지연이 남으면 볼륨 증설/분리를 적용한다. 20GB라는 용량만으로 IOPS 한계를 추정하지 않는다.
- 필요한 중복 코드만 공통화한다. 별도 pressure controller는 운영상 이득이 확인될 때 도입한다.

## 7. 검증 기준 보완

- 단순 `ParquetBatchWriter` replay 대신 **발행 → 실제 NATS → consumer → delivery 원장/manifest → Parquet → ACK → 업로드/유지보수** 전체 경로를 시험한다.
- 기존 `replay_storage_capacity.py`는 `writer.add(event)`에 stream metadata를 넣지 않아 delivery 원장을 운영과 동일하게 생성하지 않는다. 전체 수집 처리 능력 시험으로 간주하면 안 된다.
- 운영 부하 위에 2배 replay를 추가한 결과를 통제된 2배 부하 시험이라고 부르지 않는다. 백업·compaction을 포함한 조건과 입력을 분리해서 기록한다. 266건/초 초기값을 검증된 최대 피크로 취급하지 않는다.
- 일시적 probe 실패는 유효한 안전 여유가 있을 때 제한적으로 견디되, 정보 만료·실제 capacity 초과·publisher 실패에서는 안전하게 멈추는지 확인한다.
- Parquet 기록·DB 확정·ACK·원격 업로드 경계에서 강제 종료 후 복구를 확인한다. ACK된 이벤트는 복구 가능한 확정 파일에 있어야 하며, stream generation이 바뀌면 이전 ACK floor를 재사용하지 않는다.
- 중복 없는 논리적 확정과 임시/고아 물리 파일을 구분한다. 재전달, 발행 ACK 유실 후 재발행, 재시작 및 24시간 원장 만료를 함께 시험한다.
- 복구 성공은 수집기의 한 건 발행이 아니라 종목별 최신 데이터, 지속 ACK, 안정된 적체와 원격 검증으로 판단한다.
- 이후 48시간 로그는 정상 발행 시간과 정지 시간을 분리해 평가한다. 수집이 멎은 상태의 낮은 적체·메모리를 처리 능력의 증거로 사용하지 않는다.

## 8. 기존 작업 기록의 결론 정정

기존 기록의 “2배 writer replay 때 공간이 줄었으므로 20GB 볼륨이 코인 2배 부하를 감당하지 못했다”는 결론은 근거가 충분하지 않았다. 해당 시간에 주식 전체 DB 백업이 겹쳤고, replay도 전체 운영 경로를 재현하지 않았다. 정확한 판정은 **시험 도중 안전 기준에 걸려 중단됐으며, 코인 자체 처리 능력은 미검증**이다.

또한 “정상 신규 메시지는 SQLite 조회를 하지 않는다”, “백업은 하루 1회로 변경됐다”는 설명은 각각 delivery-key 조회와 코인 역할에만 해당한다. 전체 시스템에 적용된 것으로 설명하면 부정확하다.

최종 원인 표현은 **공유 디스크의 유지보수 부하와 저장 경로의 잔여 I/O 비용, 상태 조회 실패의 불명확한 분류, 현재 공간 예산에 맞지 않는 재개 조건이 결합했다. 17:02 재중단의 최초 트리거와 하드웨어 지속 처리 한계는 아직 미확정**으로 수정한다.
