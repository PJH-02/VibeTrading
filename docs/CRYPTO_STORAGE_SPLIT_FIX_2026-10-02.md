# 코인 수집 반복 정지 원인과 수정

2026-10-02 KST, 서버 `hyfe`. Binance·Bybit·Bitget의 BTCUSDT·ETHUSDT·SOLUSDT 수집기를 실제 운영 부하에서 조사하고 수정했다. 최종 디스크 분리는 14:55:12에 완료했다. 15:32까지 약 37분 동안 세 거래소가 정상 수집했고, 코인 저장기는 660,475건을 처리했다. 코인 서비스 5개의 오류·경고·압력 정지 로그, 컨테이너 재시작 및 OOM 종료는 0건이었다.

## 확인한 원인

20GB 데이터 디스크에 일반 시장 SQLite, 코인 SQLite, NATS, Parquet 쓰기가 집중되어 있었다. 수정 전 I/O 대기 압력 `full avg10`은 약 74%였고, 같은 디스크를 쓰는 시험 구성에서도 약 77%였다. 저장 지연으로 NATS가 쌓여 `nats_stream_capacity` 안전 정지가 발생했다. 별도로 데이터 디스크 여유 공간도 4GiB 보호선 부근이었다.

이 부하가 계속되는 동안 기존 보관 작업은 I/O 압력 5% 이하를 기다렸다. 따라서 업로드와 검증된 파일의 공간 회수까지 중단되어, 여유 공간이 줄고 수집을 멈춘 뒤에야 정리가 가능한 순환이 생겼다. 보관 프로세스의 idle I/O 우선순위와 2MiB SQLite 캐시도 지속적인 저장 부하에서 정리를 늦췄다. 코인 전송 원장은 24시간, 재전달 중복 판별 인덱스는 48시간을 유지해 작은 디스크에 비해 상태가 빠르게 커졌다.

NATS만 10GB 디스크로 옮긴 초기 시험에서도 저장기가 준비 상태를 잃었고, 코인 대기열은 114,055,233 bytes로 128MiB 한도의 약 85%까지 증가했다. 최종 구성에서는 코인 SQLite를 옮겼다. 다운로드 작업의 존재만으로 원인을 추정하지 않고, 디스크별 지연·프로세스별 쓰기·저장/ACK 진행·보관 게이트를 확인했다.

## 적용한 구성

| 자원 | 최종 사용 |
|---|---|
| 10GB 시스템 디스크 `/dev/vda2` | 코인 SQLite 및 상태: `/srv/vibetrading-crypto-state` |
| 20GB 데이터 디스크 `/dev/vdb` | NATS, 일반 시장 SQLite, 코인 및 일반 시장 Parquet |
| 여유 RAM | 코인 저장기·보관기 SQLite 캐시 각각 128MiB, 일반 시장 저장기 캐시 128MiB |

사용 중인 프로세스가 참조하지 않는 VS Code 서버의 구버전 바이너리 캐시 2,669,633,536 bytes를 회수했다. 사용자 설정·확장·데이터와 활성 에이전트는 보존했다. 확보한 공간에 코인 DB를 이동했고, 파일별 SHA-256·소유자·권한을 검증했다. 새 저장기가 정상 기동한 뒤 20GB 디스크의 비활성 DB 중복 사본만 제거했다.

보관 작업을 다음과 같이 나누었다.

- 업로드와 검증된 파일의 공간 회수: I/O 압력 90% 이하에서 작은 배치로 진행.
- 원장 정리: I/O 압력 70% 이하, 저장 대기 수 8,192 이하에서 진행. 서버 ACK 및 원격 복구 증명이 필요하다.
- 전체 DB 백업과 orphan 전체 탐색: 기존의 엄격한 5% 기준을 유지하고, 압력이 높으면 DB를 열거나 파일 트리를 순회하기 전에 양보한다.
- 보관기는 `ionice -c2 -n7`로 변경했다. 업로드 8개, 복구 문서 8개, 인덱스 run 은퇴 8개, 원장 정리 8,192건 단위로 처리한다. 밀린 작업의 재시도 대기는 5초다.
- 원격 저장 연결을 재사용하고 단계별 처리 시간을 기록한다. 저장기 내부 재시도 오류는 별도 `storage_errors.jsonl`에 보존한다.

코인 로컬 전송 원장은 6시간, 실시간 재전달 인덱스는 12시간으로 제한했다. 수집 원본 Parquet는 기존 원격 검증 절차를 통해 보존한다. 시간 창 변경을 위해 저장기를 정지한 상태에서 현재 수집 세대의 검증된 복구 문서로 정확한 인덱스 486,128건을 복원했다. 앞선 사용자 요청으로 삭제한 과거 수집 세대는 복원하지 않았다. 최종 세대는 `dc392454959d45c1ab939046cdce01dd`다.

코인 서비스 5개 모두 10GB 상태 디스크를 별도로 검사한다. 20GB 디스크는 4GiB, 시스템 디스크는 1GiB를 보호하며, 재개에는 각각 추가 512MiB·256MiB의 여유가 필요하다. 코인 NATS 한도 128MiB와 WAL `FULL` 동기화는 유지했다.

재부팅 복구도 수정했다. 기존 systemd 서비스는 비활성화되어 있었고 올바른 Compose 파일이 없는 디렉터리를 사용했다. 최종 릴리스를 명시하는 부팅 서비스를 활성화했으며, 독립적으로 운영하는 다른 서비스를 제거하는 `--remove-orphans`를 사용하지 않는다. 일반 시장 저장기는 기존 이미지·명령·마운트·DB를 유지하고 캐시 설정만 변경했다.

텔레그램 상태 조회에도 새 코인 상태 디렉터리를 읽기 전용으로 마운트했다. 기존 이미지·명령·환경과 기존 마운트를 유지했다. 텔레그램 컨테이너 안에서 새 저장기의 준비 상태와 약 0.28초 전 갱신된 heartbeat를 직접 확인했다. 검증용 메시지를 보내지는 않았다.

## 검증과 관찰 범위

최종 코인 이미지: `sha256:a0832388c6645b63c2a551001434671c809000e282da85a09031a24142fdcab8`, revision `r2-split-db-938b277a55e1e480`.

수정한 런타임 파일 5개와 배포 이미지의 파일 해시를 검증했다. 관련 회귀 시험은 PC Python 3.10에서 110개, 최종 서버 이미지 Python 3.12에서 동일한 110개가 통과했다. 압력 중 원격 파일 검증/회수, 미검증 파일 보존, 복구 검증 실패 시 정리 금지, ACK/세대 보호, 두 디스크의 보호 공간과 재개 기준을 포함한다.

15:03에 최종 기동 이후의 Parquet 118개를 읽어 3개 거래소 × 3개 종목 × 4개 데이터 유형(거래·호가·펀딩·미결제약정) 모두 실제 저장됐음을 확인했다. 다른 거래소·종목 조합은 포함되지 않았다. NATS 이동 전후에는 모든 스트림과 소비자의 영속 설정·생성 식별·시퀀스·ACK 위치·잔여 메시지가 같음을 확인했다.

15:01 → 15:13 관찰에서 코인 저장기의 처리 메시지는 93,350 → 336,475, ACK는 89,656 → 328,471로 증가했다. 업로드 대기 Parquet는 201 → 1개, 미검증 복구 문서는 680 → 72개로 감소했다. 최근 코인 NATS 점유율은 약 8%, 서버 미전달 대기는 2건이었다. 원격 검증 이후에만 ACK 및 공간 회수를 진행한다.

15:13의 30초 측정에서 10GB 디스크의 쓰기 지연은 약 1.27ms, 가동률은 약 0.49%였다. 20GB 디스크는 쓰기 지연 약 89ms, 가동률 약 99%로 여전히 바쁘다. 디스크 분리로 코인 SQLite가 이 지연을 직접 받지 않게 했다. 여유 공간은 데이터 디스크 약 5.78GiB, 시스템 디스크 약 1.76GiB이며, 사용 가능한 RAM은 약 1.68GiB였다. 코인 DB 파일은 약 1.82GiB로 유지되고 내부 재사용 가능 페이지가 증가했다.

보관 주기 한 예는 4.595초였다. 업로드 8개, 복구 문서 업로드 8개, 원장 8,192건 정리 및 인덱스 run 8개 은퇴를 완료했다. 장기 운영 관찰을 대체하는 시험은 아니며, 아래 최종 관찰 증거의 시점까지 확인한 결과다.

15:32 최종 확인에서는 코인 NATS 점유율이 13.9%, 서버 미전달 대기가 0건이었다. 업로드 대기 Parquet와 미검증 복구 문서도 0개였다. 처리 660,475건 중 ACK 완료는 655,695건이며 나머지는 정상 배치 저장 중이다. DB 재사용 가능 페이지는 첫 관찰 15,200개에서 73,266개로 증가했고 파일 페이지 수는 476,928개로 유지됐다. 데이터 디스크 여유 공간은 약 5.70GiB, 시스템 디스크는 약 1.76GiB, 사용 가능한 RAM은 약 1.58GiB였다. 새 상태 디스크의 쓰기 지연은 1.26ms였다. 일반 시장 서비스가 사용하는 20GB 디스크의 높은 I/O 부하는 잔여 사항으로 남아 있다.

SKHYUSDT·SKhynixUSDT 등이 사용하는 일반 시장 DB를 교체하거나 삭제하지 않았다. DB inode와 보호한 export 파일들의 inode·크기·mtime을 전후 비교했다. 수집 원본과 export tar는 보존했다.
